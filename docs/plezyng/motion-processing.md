## Product behavior

The device-local **Motion smoothing** setting has three requests:

| Request | Effective behavior |
| --- | --- |
| **Off** | Preserve the player's configured cadence and output. |
| **MPV** | Use MPV display-synchronized temporal resampling where the active MPV output supports it. |
| **Neural** | Use the connected native or model-backed interpolator on the active decode/presentation path. Apple uses VideoToolbox for supported streams; eligible Android MPV paths try ANVIL-S/M with QNN HTP, then LiteRT NPU/GPU packs; Windows/Linux attach the PME model filter when the verified model pack is installed. Windows uses its bundled Windows ML runtime and catalog providers; Linux uses its selected ORT runtime/providers. Unsupported content falls back to MPV smoothing where available. |

Neural presets are **Performance**, **Balanced**, and **Quality**. On macOS and iOS device builds, Apple's cadence-aware `VTFrameRateConversion` path uses mpv's display-slot schedule to choose intermediate timestamps, capped by preset budgets of one, three, or seven generated frames. When display-slot data is unavailable or the low-latency fallback is active, presets use uniform 1/3/7-frame grids. This follows the active display cadence instead of forcing a fixed 2×/4×/8× multiplier. Desktop Performance uses bundled 540p ANVIL-S, Balanced uses upstream 1080p ANVIL-S, and Quality uses upstream 1080p ANVIL-M; Android Performance/Balanced use ANVIL-S and Quality uses ANVIL-M; Android selects burst power for Performance and sustained power for Balanced/Quality. The desktop PME filter passes the selected preset to ONNX Runtime's QNN provider as `burst`, `balanced`, or `sustained_high_performance`; Windows resolves QNN through the Windows ML provider catalog. That HTP setting applies only when QNN actually owns the session; OpenVINO, CUDA, DirectML, Vitis AI, and CPU runs report it as not applicable. The MPV fallback does not consume the Neural preset. Diagnostics report the HTP mode only after the QNN runtime accepts it. VideoToolbox does not expose reliable per-frame ANE/GPU placement through this API.

**Only when plugged in** is an opt-in Neural power guard, enabled by default. It checks the platform battery state before provider setup and listens for a switch to battery during playback. When the platform confirms battery operation, Apple interpolation is disabled and model-backed MPV filters are removed; MPV smoothing remains active where available. It resumes Neural on the next item after external power returns rather than hot-starting a provider mid-stream. Unknown or unsupported power status remains eligible so a battery-less desktop or TV is not treated as unplugged.

Motion processing is independent of **Match Content Frame Rate** and **Match Refresh Rate**. Those choose display cadence; this engine processes or synthesizes video frames for that cadence.

## Implemented in PlezyNG

`MotionProcessingService` applies `video-sync=display-resample`, Mitchell temporal scaling, and interpolation before each MPV `loadfile`, including reused-player episode transitions. It saves and restores the user's original MPV timing properties. Windows/Linux/Android MPV smoothing is limited to progressive SDR VOD up to 1080p at 24/30 fps. Desktop Neural accepts only progressive SDR H.264 at 1280×720 or 1920×1080 and uses the PME filter's matching-shape and bounded-resampling contract. Android Neural's midpoint frames also use MPV's display-sync scheduler. At playback startup the service prepares the known Windows/Linux MPV paths; diagnostics resolve the request against the active `current-vo`, actual interpolation state, and scan type from the selected source video stream. An explicitly interlaced source is reported in the performance overlay and resolves to Off; missing scan metadata remains unknown and does not make setup eligible.

The separate `MotionClarityService` preserves measured display-rate precision when configuring FFmpeg `minterpolate`. It passes common 1000/1001 cadences as exact rational rates, accepts 47.952 Hz as the fractional equivalent of the 48 Hz minimum, and ignores non-finite reported frame rates.

- **Windows:** the embedded MPV output is `gpu-next`.
- **Linux Wayland:** embedded `vo=libmpv` receives the active monitor rate through `display-fps-override`. After a successful EGL swap, the runner calls `mpv_render_context_report_swap` so libmpv receives presentation timing.
- **Android MPV:** an explicit MPV request asks the native video-output arbiter to move eligible progressive SDR video up to 1080p at 24/30 fps from direct MediaCodec presentation to its GPU renderer. The arbiter owns surface handoff and keeps the configured decoder choice; Off removes only the motion request, allowing any other GPU requirements to remain active. Neural first tries ANVIL/QNN on a supported Snapdragon path, then LiteRT CompiledModel on an available NPU, then LiteRT GPU. LiteRT rejects CPU-partitioned sessions; when setup fails, the service configures MPV smoothing. ANVIL's `gpu-next` route uses software decoding with exported motion vectors. Live, transcoded, HDR/Dolby Vision, interlaced, and out-of-scope cadence/resolution remain on the configured output.
- **Apple AVFoundation:** the opt-in `avfoundation-motion-interpolation` option and `avfoundation-motion-preset` tier configure an MPV VideoToolbox bridge. macOS 15.4+ and iOS/iPadOS 26+ device builds prefer `VTFrameRateConversion` when the runtime reports it supported; mpv's `video-sync=display-resample` schedule supplies each source frame's display-slot count, and the processor accepts caller-selected phases. If that processor is unsupported or cannot start, the native bridge falls back to `VTLowLatencyFrameInterpolation` when supported. tvOS and compile targets without the general API use the low-latency path directly; it offers uniform 1/3/7-frame grids. Session creation stays off the render thread. It inserts generated frames before the current source sample and stays off for HDR/Dolby Vision, interlaced, non-24/30 fps, over-1080p, non-normal playback rate, OSD-composited, or geometry-rendered frames. It skips a pair when its recent processing time cannot fit the current presentation budget. The `video-out-interpolation` property reports `ready` or `active` only when the current stream passes those path/cadence guards; unsupported content, seeks, and presentation resets revoke eligibility until the path is valid again.
- The app arms Apple's Neural request before the file opens only when the selected version reports progressive SDR video at 24/30 fps within the initial 1080p scope and the active VO is AVFoundation. The native VideoToolbox path still checks actual frame format, HDR transfer, geometry/OSD state, and timing budget per pair. The eligibility decision is retained for the session so an in-player mode or preset change cannot bypass the open-time gate; a missing version, dimensions, selected video track, scan type, or cadence leaves Neural off.
- **Diagnostics:** the performance overlay reports actual video output, display rate, `video-sync`, interpolation state, source/render frame rates, and drops. Android ANVIL and desktop PME report cumulative generated-frame and decoded source-frame counts; the overlay shows the measured synthesis-to-source ratio. Android ANVIL also reports the QNN inference p95 over the latest 64 samples, deadline misses, scene-cut bypasses, and the power mode accepted by the HTP runtime. Desktop PME reports its selected HTP mode only when QNN is the active provider; non-QNN providers identify that field as not applicable. It resolves the requested mode against the active output, including ExoPlayer and unsupported MPV paths, and distinguishes a Neural request falling back to MPV from Neural inference.
- **Typed playback report:** `PlaybackCapabilityReport` groups the active output, decoder, pixel format, coded source dimensions, source FPS, HDR classification, Dolby Vision source profile, display/render rates, dropped frames, renderer state, neural-provider telemetry, adaptive PME phase budgets and timing source, and the cached platform thermal tier. The performance overlay shows an HDR yes/no row only when source transfer evidence supports that classification. HDR is true only for recognized PQ/HLG transfers, MPV HDR10 static metadata, or ExoPlayer HDR metadata; it is false only for recognized SDR transfers and unknown for ambiguous or unreported transfers. In particular, linear transfer is not assumed to mean SDR. Known HDR/Dolby Vision, over-1080p, or out-of-scope cadence resolves the effective mode to Off in diagnostics. Missing metadata stays unknown; it is not converted into a claim that the stream is SDR. Provider readiness is kept separate from observed generated output. The Android filter reports `qnn-htp-vN-ready` / `qnn-htp-vN` or `litert-npu-ready` / `litert-npu` and `litert-gpu-ready` / `litert-gpu`; the ready suffix appears before the first successful inference and the active name only after execution. It also reports generated-frame count, p95 inference latency, misses, and scene-cut bypasses. Windows/Linux read the matching `plezy-pme` filter metadata when available. ExoPlayer reports its active surface and decoder, while webOS is identified as its native player path without inferring access to the TV's MEMC controls. An installed or initializing provider is never displayed as generated-frame activity.
- **Thermal governor:** Android samples `PowerManager` status on API 29 and later before ANVIL setup and polls every five seconds while Neural is active. Moderate or higher pressure removes ANVIL and falls back to MPV smoothing when available. Apple reads `ProcessInfo.thermalState`; serious or critical pressure turns off VideoToolbox interpolation. If a provider transition fails, the report does not claim Neural paused and the governor keeps monitoring and retries. A new item checks the OS tier again before preparing Neural. Missing status fails open. The overlay shows the most recently reported tier.
- **Live playback:** live opens restore the saved MPV timing properties. The diagnostics resolver also receives the live/VOD state and reports motion processing as off for live playback, even when a global request is saved.
- **Settings:** Off, MPV, Neural, and the Performance/Balanced/Quality neural presets are selectable across players. In an already-active supported desktop or Android Neural session, preset selection replaces the filter/provider live without stopping or reopening the media; the service serializes the transition and attempts to restore the previous preset if setup fails. Initial Neural activation and unsupported sessions remain staged for the next media open. Android Neural may switch an eligible H.264 stream to software decoding to expose motion vectors and CPU-readable frames. Android MPV can change only the video output for its eligible range and retains the decoder preference. Off restores the configured output. Unsupported streams continue normal playback and report the effective fallback.

## Runtime and model architecture

There is no single hardware provider that works on every platform. The engine needs one model/session contract with provider adapters and a platform-owned frame bridge:

1. **Common inference API:** PME is compiled against ONNX Runtime C API v27 or newer. Windows pins the stable Windows ML 2.4.89 package, which supplies ONNX Runtime 1.27.1 and the Windows ML C execution-provider catalog. The Linux AMD manifest selects the built-in MIGraphX provider; only that explicit marker permits PME to request C API v23 for AMD's ROCm 7.2.1 ORT 1.23.2 wheel. The pinned ANVIL-S model completed inference on the RX 7900 XT with CPU fallback disabled. AMD's newer ORT 1.29.0 / ROCm 10.1 plugin lists `gfx1100` Radeon GPUs as supported, but the pinned ANVIL-S graph currently executes entirely on CPU through that plugin, so it is not used for this model. Windows orders catalog-managed QNN NPU, OpenVINO NPU, Vitis AI NPU, QNN GPU, NvTensorRtRtx GPU, MIGraphX GPU, and OpenVINO GPU, then bundled DirectML GPU. Linux registers OpenVINO, AMD MIGraphX, CUDA, and WebGPU providers in manifest order. The standalone `onnxruntime-ep-openvino` Plugin EP is used where supplied; the deprecated in-tree OpenVINO EP is not packaged. Linux runtime lookup accepts `PLEZY_PME_RUNTIME_DIR` before checking the app bundle; it expects PME, ONNX Runtime, the provider manifest, and any listed provider plug-ins in that directory. For AMD multi-GPU systems, `ROCR_VISIBLE_DEVICES` can be set for the PlezyNG process to limit which devices the runtime sees; provider device IDs are relative to that visible set. DirectML uses ORT's provider API with sequential execution and memory-pattern allocation disabled. Catalog and plugin providers are accepted only when ONNX Runtime assigns the model output to the requested provider/device; CPU EP fallback is disabled for accelerator sessions. Apple uses its native VideoToolbox interpolation route.
2. **Apple native effects:** `vo_avfoundation` has a native `VTFrameProcessor` bridge. On supported macOS and iOS device builds, `VTFrameRateConversion` accepts arbitrary phases; the bridge uses mpv's `num_vsyncs` schedule to select display-slot timestamps and caps synthesis to the selected preset budget. If the general conversion processor is unsupported or fails to start, the bridge falls back to the low-latency API; tvOS and targets without the general API use that uniform interpolation grid directly. The provider initializes off the render thread, accepts the OS-reported CVPixelBuffer formats, inserts generated frames before each source sample, and exposes `video-out-interpolation` states. All paths accept progressive SDR 24/30 fps streams up to 1080p at normal playback rate, avoid OSD-composited and geometry-rendered frames, and bypass when the measured deadline budget is too small. Dolby Vision and HDR are excluded. Apple's VTFrameProcessor API debuted on macOS 15.4 and is available on iOS 26; each processor's runtime support, dimensions, and pixel formats are checked. The provider reports VideoToolbox; its API does not expose reliable per-frame ANE/GPU placement.
3. **ANVIL model and Android HTP path:** ANVIL-S/M is the selected MIT model family; RIFE remains a benchmark reference. ANVIL refines frames prealigned from H.264 decoder motion vectors, so the model file alone is not a frame interpolator. The Android filter is carried as `0142-android-anvil-qnn-filter.patch` plus `0144-android-anvil-litert-provider.patch` in the pinned mpv-build Android series. It preserves the QNN HTP context route and adds LiteRT CompiledModel over the same float NHWC ANVIL input/output contract. It requires software H.264 decode with motion-vector export and initializes the selected runtime asynchronously. A coarse YUV scene-cut gate passes suspicious transitions through and exposes its bypass count in filter metadata. QNN contexts are keyed by SoC, HTP architecture, and fixed shape; LiteRT model variants are separately pinned by shape, provider class, byte count, and SHA-256.
4. **Android LiteRT providers:** the Android app packages the LiteRT 2.3.0 C++ runtime, GPU accelerator, and Maven runtime AARs for Qualcomm, MediaTek, Google Tensor, and Intel OpenVINO after checksum verification. ANVIL's model pack uses static W8A8 quantization for JIT NPU and float32 for GPU; the default pack includes target-specific Google Tensor G5/G6 AOT exports at 720p, while Samsung AOT remains a separate provider package; every target-specific record carries its exact SoC in the manifest. Android capability reporting intersects packaged provider libraries with the reported SoC family and ABI, rather than presenting every packaged plugin as usable on every device. Google Tensor selection requires a matching Tensor_G5 or Tensor_G6 AOT record; the generic JIT record is never selected there. The C ABI selects NPU first, rejects sessions with CPU execution, then tries the float GPU model. The filter reports only `litert-npu` or `litert-gpu` after that provider executes. The performance overlay names Qualcomm AI Engine Direct, MediaTek NeuroPilot, Intel OpenVINO, Samsung Exynos, or the exact Google Tensor generation from the selected NPU model record; a GPU fallback remains identified as `litert-gpu`. It uses aligned host buffers and currently copies into LiteRT tensors; AHardwareBuffer zero-copy is not claimed for this software-decoded motion-vector path. Android NNAPI is not used. LiteRT documents Exynos E9955/E9965 support. Samsung packaging accepts both LiteRT provider plugins and the matching LiteCore Android shared libraries through `PLEZY_LITERT_SAMSUNG_RUNTIME_ROOT`; the LiteCore libraries are staged as app assets, copied into app-private storage, and exposed to LiteRT through `EXYNOS_AI_LITECORE_ROOT`.
5. **GPU processing:** the ANVIL Android path uses Vulkan for prealignment and output composition. PME uses GPU compute for frame packing, flow upsampling, timestamp-specific warps, and fusion so the model provider can focus on flow refinement. GPU shader scaling already present in Plezy remains a separate spatial-enhancement path. RIFE/ncnn is a comparison tool, not the selected shipping model.
6. **NPU and GPU adapters:** ONNX Runtime supplies the shared desktop model API. Android uses QNN HTP and LiteRT CompiledModel. Windows obtains QNN, OpenVINO, Vitis AI, NvTensorRtRtx, and MIGraphX from the Windows ML catalog, with its bundled DirectML GPU provider as fallback; Linux can select OpenVINO, AMD MIGraphX, NVIDIA CUDA, or the cross-vendor WebGPU plugin through the runtime manifest. The WebGPU runtime uses Vulkan on Linux and confirms a requested GPU by its hardware vendor/device IDs. Provider labels come from the runtime's model-output provider/device report, not from a platform guess. The local ANVIL graph executes on the RX 7900 XT through WebGPU with CPU fallback disabled; its short inference measurement is not a frame-budget qualification. webOS and Tizen retain native playback paths; app-controlled interpolation needs a controllable frame-processing interface from those TV platforms.
7. **MPV renderer fallback:** display-synchronized temporal interpolation is available on supported outputs. The Android service configures renderer interpolation before opening the stream so it remains active if ANVIL's asynchronous provider cannot open. The desktop PME filter bypasses model output after cuts, unsupported cadence, missing motion vectors, provider errors, or missed deadlines; MPV smoothing remains available where the renderer supports it.

The common native boundary is `libpme`, a stable C ABI used by the MPV `vf_plezy_pme` filter. The filter owns decoded-frame pairs, timestamps, generated frames, flushes, and bypass decisions. Provider libraries and model formats stay behind that ABI. Frame processing occurs before subtitle and OSD composition so text and graphics are not interpolated.

The initial desktop adapter emitted a single midpoint frame (2×) on one worker. The current local MPV patch series extends it to up to one, three, or seven generated display phases per source pair and adds a bounded, ordered two-slot scheduler. Parallel pair processing is enabled only when CUDA or DirectML opens two equivalent provider sessions; providers including AMD MIGraphX remain single-flight. For a matched source PTS, patch 0161 uses MPV's final `num_vsyncs` after A/V correction and maps each phase to an in-range display-slot timestamp; startup and reset retain the deterministic nominal-grid fallback. The overlay reports which timing path supplied the phases. These patch-series changes and their package builds remain local candidates; the PlezyNG lock still points to the published MPV artifacts. The filter scales frames to the selected static model shape, runs CPU preprocessing or optional Vulkan preprocessing, invokes ONNX Runtime, reconstructs the model-resolution output, and upscales synthesized output to source dimensions. Its source-pair deadline includes dispatch, workspace allocation, preprocessing, inference, and reconstruction; when work misses its budget or cannot be queued, the filter preserves the source frame and disables Neural for that pair. The pinned Linux app artifact still needs rebuilding to enable Vulkan. The local RX 7900 XT qualification build enabled Vulkan and processed the complete 540p model-resolution path with MIGraphX, which remains single-flight. Windows can also select AMD Vitis AI for a supported Ryzen AI NPU or DirectML for a supported GPU when the corresponding provider-enabled ORT runtime is packaged and the model is accepted by that provider. The app selects software decoding for this route because hardware decoders do not consistently export FFmpeg motion-vector side data. The local 540p Performance path met the 1080p24 filter deadline in repeated playback; visible presentation, visual quality, and other presets remain unqualified.

```text
MPV decoder → PME frame filter → video output
                  │
                  ├─ GPU resize / color packing
                  ├─ NPU or GPU flow inference (once per source-frame pair)
                  ├─ GPU flow warp and occlusion-aware fusion (per display timestamp)
                  └─ cut / confidence / deadline checks → synthesized frame or source passthrough
```

The engine should reuse one flow result for every output timestamp between a source-frame pair. A GPU performs flow upsampling, warping, and fusion; the NPU is used for operators it can execute efficiently. Scene cuts repeat the source frame. Low confidence, occlusion, deadline misses, thermal pressure, seek, or display changes bypass synthesis and return to MPV smoothing or source passthrough. Model warm-up must be asynchronous and never block playback startup.

## Enhancement modes

The planned session and provider scheduler will handle single-frame enhancement:

- **Restore:** deblocking and debanding for low-bitrate transcodes.
- **Upscale:** neural super-resolution remains planned. The existing MPV ArtCNN/NVScaler presets remain available on GPU MPV outputs, and Android ExoPlayer now has a separate opt-in Lanczos GL resampling preset for spatial enlargement. Lanczos is a scaler, not a neural model.
- **Order:** Restore → Upscale → Interpolate. Interpolation runs on cleaned frames; subtitles, OSD, and UI remain after video processing.
- **ExoPlayer:** Media3 GL effects provide single-frame spatial resampling. Neural Restore/Upscale needs a model-backed effect path; MPV owns timestamped interpolation until ExoPlayer receives a scheduler that can emit intermediate frames.

HDR10 is introduced only after the processing path preserves its transfer function and color metadata. Dolby Vision stays on the existing route until the filter is proven not to discard or corrupt its RPU/enhancement-layer behavior. The system falls back for Live TV and interlaced content unless a route implements their timing and field semantics.
